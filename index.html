I work across the whole path of data. I take data from where it starts, such as ad platforms, website tracking and seller reports, and move it into a database or warehouse with scheduled jobs and SQL. Then I build the dashboards and reports that teams use to follow their campaigns, websites and sales.

This page shows how the data flows, nine projects, recreations of twelve of my dashboards, a sample quarterly report, my GA4 tracking work, and short code examples. Client names and real numbers are left out, so every chart here uses sample data.

Case studies

Data engineering · AWS, PostgreSQL

Seller reports, from upload to weekly review

Problem
Weekly business reviews needed sales, advertising, fees and inventory for each product in one table. The team built it by hand, copying each Seller Central CSV into Excel, and every report had its own layout.
Data
10 report types, including sales, sponsored ads, transactions, orders and two inventory reports.
What I built
A Lambda function that runs when a file lands in S3. It finds the report type from the file name, skips extra header rows, cleans the columns, loads the rows into PostgreSQL on RDS, and moves the file to a processed folder. A stored procedure adds only rows the archive doesn't have yet, and a SQL view joins every report by brand, day and product. The database sits in a private network, so I wrote the team's guide to reach it through an SSH tunnel in VS Code, with a query that checks new uploads arrive.
Outcome
No more copying CSVs into Excel: one table per brand, day and product with ad spend, sales, conversion rate, inventory cover and fees. New reports show up as soon as they're uploaded, every brand is reviewed from the same numbers, and fees on orders with several products count once.

Data engineering · AWS, Snowflake

Monthly brand reports on a schedule

Problem
Each brand needed a monthly report by product, with weekly trends and a comparison with the month before. Data shared with us in Snowflake also had to reach the reporting database.
Data
Up to 16 Amazon reports per brand each month, saved in S3 by report type, brand and month: sales and traffic, sponsored ads, orders, transactions, listings, inventory, search performance and SKU economics. Daily, product and search query performance shared in Snowflake.
What I built
A monthly Lambda job for each brand, started by its own EventBridge rule instead of by every file upload. It writes nothing if a required report is missing and skips months already done. It writes five files, including a summary, a by-product file, a weekly series and a calendar of Sunday-to-Saturday retail weeks, each with a timestamped backup. In Snowflake, scheduled tasks refresh six mirror tables, and a sync job copies only new rows into PostgreSQL.
Outcome
Each brand's monthly report builds itself on a schedule, with weekly, by-product and summary totals that match exactly. A month with a missing report is held back instead of showing wrong totals, and the mirror tables match their source row for row. I tested in a separate bucket first and watched each run in CloudWatch.

Dashboards · GA4, Looker Studio Dashboard HDashboard I

One dashboard for websites in seven countries

Problem
A brand ran websites in seven countries, plus a site shoppers reach by scanning the pack. It needed a global view and the same view for each country.
Data
GA4 for each country site: channels, pages, scroll depth, CTA clicks and purchases. Scan data for the pack site.
What I built
16 views, global and per country, for the websites and the scan site. Each website view follows five steps: Catch, Connect, Convert, Webshop and Continue. The scan views show weekly scans, scans by city tier, scan errors and accuracy, and a product breakdown. A glossary page defines every metric.
Outcome
All seven markets in one dashboard, on the same metrics. Teams can compare markets side by side, follow each one through the same five steps, and check what any metric means in the glossary.

Web analytics · GA4, GTM, Looker Studio Dashboard ADashboard BDashboard C

Measuring a visitor journey, stage by stage

Problem
A health-education website wanted to see how far visitors moved, from first interest to taking action, not just how many came.
Data
29 GA4 events tracked through GTM, such as polls, guide downloads, video plays and finder searches, by channel and device.
What I built
I grouped the events into six journey stages and their key actions. A monthly Looker Studio dashboard shows each stage's rate and sessions against the period before, plus traffic by channel and device. Each quarter I wrote a highlights deck with an executive summary, including how much the cookie consent banner limited what GA4 could measure.
Outcome
The team can see how far visitors get, not only how many arrive. Each stage's rate shows where visitors drop off, and the quarterly deck turned the numbers into next steps for the site. The consent check showed how much traffic GA4 couldn't see, so the numbers are read with that in mind.

Event tracking · GTM, GA4, Looker Studio Dashboard EDashboard F

Pop-up survey and call-to-action tracking

Problem
A brand showed a survey pop-up across its site and three calls to action on two campaign sites. It needed to know where people saw them, where they responded, and which traffic brought responses.
Data
GA4 events for pop-up views, form submits and CTA clicks, with source, medium, device, page and product. Visits from a messaging app's in-app browser were split from the rest.
What I built
Two Looker Studio dashboards with filters for device, source, page type and product: submissions by day and hour, submission rate by page type, CTA click-through over time, and tables by CTA, device, source and channel. Submit tracking started seven weeks after pop-up tracking, so the submission rate only counts from that date, and the dashboard says so.
Outcome
The team can see where the survey and calls to action work, by page, source and device. Pages are judged by the responses they bring, not just views, and messaging-app visitors can be compared with everyone else. The submission rate stays honest because it leaves out the weeks before submits were tracked.

SEO analytics · GA4, Search Console Dashboard G

A monthly SEO report from two sources

Problem
The team wanted one monthly view of organic search: which pages held up, which searches brought people in, and the trend over a year.
Data
GA4 sessions, bounce rate and time on site by landing page. Search Console clicks, impressions, click-through rate and position by query and page, with queries in two languages.
What I built
Page groups such as home, guides, product pages and sign-up, each with month-on-month change. Query groups that split branded from generic searches. 12-month trend charts for each page group, and a table of visits referred by AI assistants such as ChatGPT.
Outcome
One monthly view of organic search, from both tools. Branded and generic searches are kept apart, each page group shows what grew or fell, and visits from AI assistants are tracked as their own source.

Digital campaigns · Datorama, BigQuery, Looker Studio Dashboard JDashboard KDashboard L

Bank campaigns, from many platforms to one view

Problem
A bank ran search, display, social and video campaigns. Each ad platform reported in its own format, and the team needed one view of spend, clicks and conversions, down to each step of the application form.
Data
Ad platform exports and website conversion tags, such as brochure downloads, lead forms and applications, combined in Datorama and BigQuery.
What I built
Three Looker Studio dashboards: a paid media overview of traffic, spend and conversions; a search report by campaign, keyword group and product; and a search and display report that follows the application form step by step, with cost per step and written insights.
Outcome
Every channel's spend and results in one place, on the same definitions. The team can see where applicants drop out of the form, what each step costs, and which sites and keywords cost the most for what they bring.

Social media analysis · Facebook groups Dashboard D

Daily tracking of liver-health Facebook groups

Problem
The liver-health program ran Facebook groups where members and admins post every day. The team needed a steady record of what was posted, by whom, and how members responded.
Data
Daily posts from members (user-generated content) and admins, with their comments and reactions.
What I built
A daily post tracker that separates member posts from admin posts and counts the comments and replies each one gets. It shows posting by day and weekday, and which admin posts start the most conversation.
Outcome
The team can see how active the groups are each day and which admin posts get members talking. Admin posts can be planned around what works.

Synthesized analysis · AI text classification (LLM) Sample deck

How treatment-ready is the community?

Problem
Beyond counts, the team needed to understand the community: what members care about, who leads the conversation, and how ready members are to act on treatment.
Data
Thousands of member posts and comments from the daily tracker.
What I built
I used our work AI tool, a large language model, as a text classifier. One fixed prompt template with set categories and a JSON answer meant every row was coded the same way: a theme such as community support, lifestyle or treatment questions, a behaviour such as asking for advice, and a treatment-readiness stage. I found the top voices, synthesized the results, and presented them in a quarterly report deck.
Outcome
A clear picture of what members need and how ready they are to talk about treatment. Each quarterly report gave the team themes to build content around and the share of members ready to ask a doctor.

How I register one

  1. Check the parameter arrives with its event in GA4.
  2. Open Admin › Data display › Custom definitions, then Create custom dimension.
  3. Give it a readable name, set the scope to Event, and enter the parameter name exactly as it's sent, such as poll_answer.
  4. Save, then use the new dimension in reports and Looker Studio.

GA4 fills a custom dimension only from the day it's created, so a parameter needs registering before its data is needed.

Python · AWS Lambda

Load each report as it arrives

A file landing in S3 starts the function. It finds the report type from the file name, loads the rows, then moves the file out of the inbox.

import io, os, boto3
import pandas as pd
from urllib.parse import unquote_plus
from sqlalchemy import create_engine

s3 = boto3.client("s3")
db = create_engine(os.environ["DB_URL"])
TABLES = {"business-report": "sales",
          "sp-ads": "ads_sp",
          "inventory": "inventory"}

def handler(event, context):
    rec = event["Records"][0]["s3"]
    bucket = rec["bucket"]["name"]
    key = unquote_plus(rec["object"]["key"])
    table = next(TABLES[k] for k in TABLES
                 if k in key)
    obj = s3.get_object(Bucket=bucket,
                        Key=key)
    df = pd.read_csv(io.BytesIO(
        obj["Body"].read()))
    df.to_sql(table, db, schema="raw",
              if_exists="append",
              index=False)
    # Move the file: raw/ to done/
    s3.copy_object(Bucket=bucket,
        Key=key.replace("raw/", "done/"),
        CopySource=f"{bucket}/{key}")
    s3.delete_object(Bucket=bucket, Key=key)

Copy only new rows, then move the bookmark

The sync reads where it stopped last time, loads only rows added since, and moves its bookmark no further than the rows it just loaded.

-- Runs in one transaction
create temp table new_rows
  on commit drop as
select s.*
from staging.search_terms s
where s.loaded_at > (
  select last_loaded_at
  from sync_state
  where source = 'search_terms');

insert into mart.search_terms_weekly
  (week_start, product_id, term,
   impressions, clicks, purchases)
select week_start, product_id, term,
       impressions, clicks, purchases
from new_rows
where week_end - week_start <= 6;

update sync_state
set last_loaded_at = coalesce(
  (select max(loaded_at) from new_rows),
  last_loaded_at)
where source = 'search_terms';

One daily table across ad platforms

Each platform names its columns differently. One model lines them up, so every dashboard reads the same table.

-- One row per day, channel, campaign
create or replace table mart.daily_ads
partition by date as
select date, 'Search' as channel,
       campaign, cost, clicks,
       conversions
from raw.search_ads
union all
select date, 'Social', campaign_name,
       spend, link_clicks, purchases
from raw.social_ads;

-- Cost per conversion by week
select date_trunc(date, week) as week,
       channel,
       safe_divide(sum(cost),
                   sum(conversions)) as cpa
from mart.daily_ads
group by week, channel
order by week, channel;

Mirror shared data on a schedule, then check it

A data provider shares Amazon seller data with us in Snowflake. A scheduled task copies it into our own tables, and a count checks the copy matches its source. The PostgreSQL sync then moves new rows to AWS.

-- Refresh our mirror of the shared table
create or replace task refresh_daily_mirror
  warehouse = reporting_wh
  schedule = 'USING CRON 0 6 * * * UTC'
as
  create or replace table
    mirror.daily_sales as
  select * from shared.amazon.daily_sales;

-- Tasks start paused
alter task refresh_daily_mirror resume;

-- The mirror must match its source
select 'mirror' as tbl, count(*) as n
from mirror.daily_sales
union all
select 'source', count(*)
from shared.amazon.daily_sales;
